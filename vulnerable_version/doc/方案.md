# 高校招生录取系统漏洞防护与研究（未防护实现版）技术方案

## 1. 项目定位
- 毕设实现范围：仅实现“未防护版本”的高校招生录取系统。
- 研究目标：在可运行系统上复现典型漏洞，并在论文中提出修复方案与安全加固设计。
- 演示方式：由作者本人本地环境演示，不要求上线部署。

## 2. 方案边界（本项目最终约束）
- 做：业务系统可用、漏洞可复现、论文有修复设计。
- 不做：完整加固版代码实现、生产级高可用部署、复杂攻防平台。

## 3. 技术选型（简化优先）
- 后端框架：FastAPI（Python）
- 数据库：SQLite（开发演示）/ MySQL 8（论文可扩展说明）
- 前端：Vue 3 + Vite（前后端分离）
- 接口测试与漏洞验证：Postman、sqlmap、浏览器开发者工具（可选 ZAP）
- 运行环境：Windows 本机（开发与答辩演示一致）

## 4. 功能模块设计（答辩够用）
1. 用户登录模块
- 角色：考生、管理员
- 能力：账号密码登录、退出

2. 考生信息模块
- 考生个人信息录入与查看
- 管理员查看考生列表

3. 志愿填报模块
- 考生填写志愿院校与专业
- 管理员查看志愿信息

4. 成绩管理模块
- 管理员录入成绩
- 考生查询个人成绩

5. 录取查询模块
- 管理员发布录取结果
- 考生查询录取状态

## 5. 漏洞设计与复现点（未防护版核心）
以下为当前代码中已存在、可复现的漏洞（与 `backend/app/main.py` 对应）：

1. SQL 注入（登录）
- 位置：`POST /api/login`
- 代码特征：使用字符串拼接 SQL（`f"SELECT ... WHERE username='{...}' AND password='{...}'"`）
- 风险：可绕过认证，直接获取用户身份（高危）
- 论文修复方案：参数化查询/ORM 条件查询，禁止拼接 SQL

2. 身份伪造与越权（认证设计缺陷）
- 位置：几乎全部接口通过查询参数 `user_id` 识别用户
- 代码特征：`get_current_user(user_id)` 直接信任前端传入的 `user_id`
- 风险：攻击者可修改 `user_id` 冒充管理员，调用管理员接口（高危）
- 论文修复方案：改为服务端签名会话（JWT/Session），`user_id` 不可由客户端自由指定

3. IDOR（对象级越权）
- 位置：`GET /api/profile/{profile_id}`
- 代码特征：仅校验登录，不校验该 `profile_id` 是否归属于当前用户
- 风险：普通考生可查看他人档案信息（中高危）
- 论文修复方案：增加“数据归属校验”（`profile.user_id == current_user.id`）或 RBAC + ABAC

4. 任意表达式执行（导入链路）
- 位置：`POST /api/scores/import`
- 代码特征：对 Excel 单元格公式字符串执行 `eval(total_raw[1:])`
- 风险：可导致服务端执行恶意表达式，属于远程代码执行类风险（高危）
- 论文修复方案：严禁 `eval`；只允许数值解析；对导入数据做白名单校验

5. 明文密码存储
- 位置：`user.password` 写入时未哈希
- 风险：数据库泄露后账号密码直接暴露（高危）
- 论文修复方案：`bcrypt/argon2` 哈希 + 唯一盐值 + 登录比对哈希

6. 弱认证防护（可暴力破解）
- 位置：`POST /api/login`
- 代码特征：无验证码、无失败计数、无账号锁定、无限重试
- 风险：可被撞库或密码爆破（中危）
- 论文修复方案：限流、失败锁定、验证码、登录审计

7. CORS 过宽
- 位置：全局 CORS 配置 `allow_origins=["*"]`
- 风险：跨站请求策略过宽，放大攻击面（中危）
- 论文修复方案：仅放行受信任域名，区分开发/生产配置

## 6. 数据库简化模型
建议核心表：
- `user`：用户账号（id, username, password, role, created_at）
- `candidate_profile`：考生信息（id, user_id, exam_no, name, id_card, phone）
- `application_choice`：志愿信息（id, candidate_id, batch, university, major, priority）
- `score`：成绩信息（id, candidate_id, subject, score, total_score）
- `admission_result`：录取结果（id, candidate_id, university, major, status, publish_time）
- `notice`：公告/留言（id, title, content, creator_id, created_at）

## 7. 开发与演示计划（建议 2 周）
第 1 周
- 完成数据库建表与基础页面
- 完成登录、信息管理、志愿、成绩、录取查询的基本流程
- 预埋漏洞点并自测可触发

第 2 周
- 编写漏洞复现实验步骤
- 采集演示截图（正常流程 + 攻击流程）

## 8. 论文写作映射（与你实现强绑定）
第 1 章 绪论
- 背景：招生录取系统涉及敏感数据，安全需求高

第 2 章 系统分析与未防护实现
- 业务流程、系统架构、数据库设计、关键代码说明

第 3 章 漏洞复现与风险评估
- 每类漏洞给出：复现前提、攻击步骤、结果截图、风险等级

第 4 章 修复方案设计（可不落代码）
- SQL 注入 -> 参数化查询/ORM
- 身份伪造 -> JWT/Session + 服务端鉴权中间件
- IDOR 越权 -> 数据归属校验 + 最小权限
- 导入执行风险 -> 禁止 `eval` + 严格类型白名单
- 明文密码 -> bcrypt/argon2 哈希存储
- 暴力破解 -> 限流、验证码、失败锁定、审计日志

第 5 章 总结与展望
- 总结成果与局限，展望后续安全增强

## 9. 答辩演示脚本（5-8 分钟）
1. 正常业务演示
- 登录 -> 填报志愿 -> 管理员录入成绩 -> 查询录取结果

2. 漏洞演示
- SQL 注入绕过登录（`/api/login`）
- 修改 `user_id` 参数冒充管理员并调用管理接口
- 访问 `/api/profile/{id}` 读取他人信息
- 导入恶意 Excel 触发服务端 `eval` 执行风险

3. 修复思路说明
- 展示“漏洞-危害-修复方案”对照表（论文内容）

## 10. 验收标准（你当前阶段）
- 系统可运行：核心业务链路可走通
- 漏洞可复现：至少 4 类漏洞稳定复现（SQL 注入、身份伪造、IDOR、导入执行）
- 论文可支撑：每类漏洞有复现证据和修复设计
