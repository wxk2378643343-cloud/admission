# vulnerable_version 漏洞说明

本文档记录 `vulnerable_version` 中保留的主要安全问题，用于后续漏洞演示、修复版对比和验收说明。

## 1. SQL 注入

后端大量接口使用 f-string 直接拼接 SQL，例如登录、查询、增删改等逻辑。

典型位置：

- `backend/main.py` 登录接口 `/api/login`
- `backend/main.py` 管理端查询接口 `/api/admin/students`、`/api/admin/plans`、`/api/admin/notices`
- `backend/main.py` 学生端接口 `/api/student/profile`、`/api/student/score`
- `backend/main.py` 志愿和录取分配相关接口

风险：

- 攻击者可构造特殊输入绕过登录。
- 攻击者可读取、修改或删除数据库数据。
- 管理端搜索参数、账号密码、公告内容等输入均可能成为注入入口。

修复建议：

- 全部 SQL 改为参数化查询。
- 禁止使用字符串拼接构造 SQL。
- 对分页、ID、枚举字段做强类型校验。

## 2. 弱认证和伪造权限

当前前端登录态存储在 `localStorage` 中，后端管理权限主要依赖请求头：

```text
X-Role: admin
```

风险：

- 攻击者可以手工构造请求头伪装管理员。
- 后端没有真实 session、JWT 或服务端 token 校验。
- 管理端接口只要带上伪造 `X-Role` 就可能访问。

修复建议：

- 登录成功后签发服务端可验证的 token。
- 后端从 token 中解析用户身份和角色。
- 禁止信任前端传入的角色字段。
- 管理端接口统一做服务端鉴权。

## 3. 明文密码存储

`users.password` 以明文保存。

涉及功能：

- 用户登录
- 学生注册
- 修改密码
- 管理员重置密码
- `/api/debug/users`

风险：

- 数据库泄露后所有用户密码直接暴露。
- 调试接口可直接泄露账号密码。

修复建议：

- 使用 `bcrypt`、`argon2` 等算法存储密码哈希。
- 登录时对输入密码做哈希校验。
- 禁止任何接口返回密码字段。
- 重置密码后只保存哈希值。

## 4. 越权访问 IDOR

学生端接口直接使用前端传入的 `user_id` 查询数据。

典型接口：

```text
GET /api/student/profile?user_id=
GET /api/student/score?user_id=
GET /api/student/admission?user_id=
GET /api/student/choices?user_id=
```

风险：

- 学生修改请求中的 `user_id` 后，可能读取或操作其他学生的信息。
- 后端没有校验当前登录用户是否等于请求中的 `user_id`。

修复建议：

- 从认证 token 中获取当前用户 ID。
- 学生端接口禁止由前端传入任意 `user_id`。
- 所有资源操作必须校验资源归属。

## 5. XSS 风险

学生公告详情页面使用了 `v-html` 渲染公告内容。

典型位置：

```text
frontend/src/views/student/StudentNotices.vue
```

风险：

- 如果公告内容中包含恶意 HTML 或脚本，学生查看公告时可能执行恶意代码。
- 如果攻击者能通过注入或弱权限写入公告内容，影响会扩大。

修复建议：

- 避免直接使用 `v-html`。
- 如必须渲染富文本，应使用白名单 HTML sanitizer。
- 管理端发布公告时过滤脚本、事件属性和危险标签。

## 6. CORS 全开放

后端 CORS 配置为：

```python
allow_origins=["*"]
```

风险：

- 任意来源页面都可以向后端发起请求。
- 配合弱认证、伪造请求头时风险更高。

修复建议：

- 仅允许可信前端域名。
- 按环境区分开发和生产 CORS 配置。
- 不要在生产环境开放所有来源。

## 7. 调试接口泄露敏感信息

存在调试接口：

```text
GET /api/debug/users
```

该接口返回：

```text
id, username, password, role, name
```

风险：

- 直接泄露所有用户账号、明文密码和角色。
- 可被用于账号接管和权限提升。

修复建议：

- 删除该接口。
- 或仅在本地开发环境启用。
- 永远不要返回密码字段。

## 8. 输入校验不足

当前很多字段只依赖前端控件限制，后端校验不足。

示例：

- 学号格式和唯一性校验不完整。
- 成绩范围缺少严格校验。
- 公告标题和内容缺少长度限制。
- 专业、批次、状态等枚举字段未全部强约束。
- 密码复杂度和长度没有限制。

风险：

- 数据污染。
- 业务状态异常。
- 配合 SQL 注入或 XSS 造成更严重后果。

修复建议：

- 使用 Pydantic 对字段长度、范围、枚举进行校验。
- 对 ID 类参数使用整数类型并校验资源存在。
- 对所有写接口增加后端校验，不依赖前端。

## 9. 缺少真实会话机制

当前登录态主要依赖前端本地存储，后端没有会话绑定。

风险：

- 登录状态可被篡改。
- 无过期时间。
- 无刷新机制。
- 无服务端注销能力。

修复建议：

- 使用服务端 session 或 JWT。
- token 设置过期时间。
- 敏感操作校验当前用户身份。
- 退出登录时使 token 失效或前端清除 token。

## 10. 敏感操作缺少审计和二次确认

敏感操作包括：

- 删除学生
- 删除公告
- 管理员重置密码
- 录取分配
- 发布录取结果

风险：

- 操作不可追踪。
- 误操作无法审计。
- 恶意管理员行为难以定位。

修复建议：

- 增加操作日志表。
- 记录操作人、时间、IP、操作对象和变更前后内容。
- 对重置密码、发布录取结果等操作增加二次确认。

## 当前说明

本版本是 `vulnerable_version`，以上漏洞用于演示和对比。业务功能已经基本补齐，但安全问题没有修复。

如果后续需要制作 `secure_version`，应优先修复：

1. SQL 注入。
2. 认证和权限校验。
3. 明文密码。
4. IDOR 越权访问。
5. XSS。
